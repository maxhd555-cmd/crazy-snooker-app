## ข้อบกพร่องและการทดสอบซ้ำ

พบความกำกวมของตัวเลือกปุ่ม **เปิดคู่มือการใช้งาน** ในสคริปต์ UAT เนื่องจากมีทั้งปุ่มในหน้าการตั้งค่าและปุ่มช่วยเหลือลอย จึงแก้สคริปต์ให้ระบุ `.settings-actions` โดยตรง แล้วรัน UAT ซ้ำครบทุกกรณีโดยผ่านทั้งหมด

> ผลการรันซ้ำ: `UAT_UI_CORE_OK`, `TABLE_UI_E2E_OK`, `UI_E2E_OK` และ `UAT_ALL_WORKFLOWS_OK`

## รายการที่เลื่อนออก

การสร้าง PromptPay QR ที่พร้อมรับเงินจริงยังรอ `PROMPTPAY_RECIPIENT` ซึ่งต้องตรวจชื่อผู้รับให้ถูกต้องก่อนเปิดใช้ ส่วนการส่งใบเสร็จอัตโนมัติยังรอผู้ให้บริการอีเมล, API key และอีเมลผู้ส่งที่ยืนยันแล้ว ทั้งสองรายการไม่ใช่ข้อบกพร่องของ UAT รอบนี้ และถูกบันทึกไว้ใน `todo.md` เพื่อดำเนินการเมื่อร้านพร้อมให้ข้อมูล

## รอบทดสอบครอบคลุมทุกปุ่มและฟังก์ชัน

การทดสอบรอบขยายใช้สคริปต์ `scripts/verify-all-controls.mjs` ร่วมกับ `scripts/verify-table-ui.mjs` และ `scripts/verify-feedback-ui.mjs` ครอบคลุมเมนูทั้งแปดหน้า, ปุ่มสินค้า POS ทุกปุ่ม, ตะกร้าและการค้นหาบาร์โค้ด, Wallet readiness, validation การจอง, คลังสินค้า, select สถานะโต๊ะทุกค่า, ตัวกรองประวัติ, ดาวน์โหลดคู่มือ, Help search/feedback validation, Interactive Tour, และส่วนควบคุมแอดมิน ได้แก่ refresh, filters, badge, เปลี่ยนสถานะ และบันทึกภายใน

พบว่าหน้าจอสถานะโต๊ะอาศัย SSE เพียงอย่างเดียวหลัง PATCH ทำให้การเปลี่ยนสถานะในหน้าจออาจแสดงช้ากว่าผลตอบกลับ API จึงเพิ่มการอัปเดต state จาก `result.table` ทันทีหลัง API สำเร็จ แล้วคง SSE ไว้สำหรับการซิงก์ข้ามหน้าจอ นอกจากนี้ปรับสคริปต์ UAT ให้รอผล PATCH จริงและจำกัดตัวเลือกที่อาจซ้ำกันใน Help/แอดมิน ก่อนรันทดสอบซ้ำ

ผลรอบสุดท้ายผ่านทั้งหมด: **22 unit tests**, production build และการทดสอบเบราว์เซอร์ทั้งสามสคริปต์ โดยรายงานทดสอบทั้งหมดถูกปิดสถานะ `resolved`, โต๊ะ 02 ถูกคืนเป็น `available`, และรอบนี้ไม่ส่ง LINE เพิ่มหรือยืนยันการชำระเงินจริง

## การทดสอบปุ่มที่มีผลจริงและกรณีถูกบล็อกด้วยการตั้งค่า

หลังได้รับการยืนยันเฉพาะจากผู้ใช้ ระบบส่งข้อความ LINE OA ที่มีป้าย `[TEST]` สำเร็จสองเส้นทาง ได้แก่ การจองจากปุ่มในหน้าจอ และแจ้งเตือนใกล้หมดเวลาจาก API จริง โดยปุ่มทดสอบใกล้หมดเวลาบน UI ถูกตรวจด้วย response mock เพื่อหลีกเลี่ยงข้อความซ้ำ การทดสอบใช้ `scripts/verify-live-line-controls.mjs` และจบด้วยผล `LIVE_LINE_CONTROLS_OK`.

ปุ่มใบเสร็จได้รับการตรวจครบทั้งเปิดใบเสร็จ, พิมพ์ผ่าน `window.print`, validation อีเมล, และเตรียม mailto ด้วยอีเมลทดสอบโดยไม่กดส่งอีเมล ผลเป็น `RECEIPT_CONTROLS_UI_OK`. กระบวนการ PromptPay ถูกทดสอบในเซิร์ฟเวอร์แยกด้วยผู้รับจำลอง: สร้าง QR, ยืนยันรายการ, และสร้างใบเสร็จได้ครบ (`PAYMENT_LIFECYCLE_ISOLATED_OK`) จึงไม่สร้าง QR หรือรายการรับเงินจริงในระบบร้าน

**ข้อจำกัดที่บันทึกไว้:** ปุ่มสร้าง QR PromptPay ในหน้า POS/Wallet แสดง error readiness ตามคาด เพราะยังไม่มี `PROMPTPAY_RECIPIENT` ของร้าน และปุ่มยืนยันรับชำระจริงจึงไม่สามารถเปิดจาก UI ได้ในรอบนี้ การส่งอีเมลจากเซิร์ฟเวอร์ยังไม่เปิดใช้เพราะยังไม่มีผู้ให้บริการและโดเมนผู้ส่งที่ยืนยันแล้ว แต่ปุ่มเตรียมอีเมลผ่าน mail client ได้รับการตรวจแล้ว

ข้อบกพร่องการทำงานที่พบจริงคือหน้าจอสถานะโต๊ะอาจรอ SSE ก่อนแสดงผล PATCH จึงแก้ให้ `changeTableStatus` อัปเดต state จากผลตอบกลับ API ทันที และคง SSE สำหรับการซิงก์ข้ามหน้าจอ ผลทดสอบซ้ำยืนยันการสลับครบทุกสถานะ `available`, `occupied`, `reserved`, และ `maintenance`.

การทดสอบได้กดทุกจุดโต้ตอบที่เปิดใช้ได้ใน UI หรือยืนยันเส้นทางฟังก์ชันใน process แยกเมื่อจุดนั้นถูกบล็อกโดย configuration. จุดที่ไม่มีการทำรายการจริงมีเพียงการยืนยัน PromptPay บนระบบร้าน (ไม่มี `PROMPTPAY_RECIPIENT`) และการส่งอีเมลจากเซิร์ฟเวอร์ (ไม่มีผู้ให้บริการ/ผู้ส่งที่ยืนยันแล้ว) ซึ่งเป็น dependency ที่บันทึกไว้ ไม่ใช่การข้ามการทดสอบโดยไม่มีเหตุผล.

## Preflight บริการภายนอก

เพิ่ม endpoint read-only `/api/integrations/readiness` และแผง **ความพร้อมบริการ** ในหน้าการตั้งค่า เพื่อบอกสถานะ PromptPay QR และอีเมลใบเสร็จโดยไม่เปิดเผยค่า credential, token หรือ recipient. แผงมีปุ่มตรวจสอบใหม่ และผ่านทั้ง unit test และ browser test (`INTEGRATION_READINESS_UI_OK`).

## สรุปกะจากประวัติรายการ

เพิ่มแผง **สรุปกะจากรายการที่แสดง** ในหน้าประวัติรายการ ซึ่งคำนวณจำนวนรายการ ยอดรวม และยอดแยกตามวิธีชำระจากตัวกรองที่พนักงานเลือก จึงใช้ตรวจยอดกะย่อยได้โดยไม่สร้างธุรกรรมเพิ่ม ปุ่มพิมพ์สรุปกะเรียกหน้าต่างพิมพ์ของเบราว์เซอร์ และผ่านทั้ง unit test ของการคำนวณและ browser test (`SHIFT_SUMMARY_UI_OK`).

## การเตรียมอีเมลใบเสร็จโดยไม่ส่งจริง

เพิ่มเส้นทางส่งใบเสร็จจากเซิร์ฟเวอร์ที่รองรับ Resend พร้อม payload ภาษาไทย, การ escape ข้อมูลใบเสร็จ, `Idempotency-Key` เพื่อป้องกันการส่งซ้ำภายในช่วงที่ผู้ให้บริการกำหนด และ header ที่จำเป็นสำหรับ API. เมื่อไม่มี `RESEND_API_KEY` หรือ `RECEIPT_EMAIL_FROM` endpoint จะตอบ `503` ก่อนเริ่มคำขอเครือข่าย และหน้าจอจะเปิด mail client ของพนักงานเป็น fallback แทน จึงไม่มีอีเมลถูกส่งในสภาพที่ยังไม่ตั้งค่าบริการ

การทดสอบ unit ของ sender ผ่านทั้งการสร้างเนื้อหา, การบล็อกก่อนตั้งค่า และรูปแบบ API request โดยจำนวน unit tests รวมเป็น **28 tests / 11 files**. Browser test ยืนยันการเปิดใบเสร็จ, พิมพ์, validation อีเมล และ fallback (`RECEIPT_CONTROLS_UI_OK`). นอกจากนี้ production build ผ่านและพบ `dist/receiptEmail.mjs` ตามที่กำหนด (`PRODUCTION_RECEIPT_EMAIL_MODULE_OK`). การส่งอีเมลจริงยังไม่ถูกทดสอบหรือเปิดใช้จนกว่าร้านจะให้ API key และผู้ส่งที่ได้รับการยืนยัน พร้อมอนุมัติการส่งทดสอบอย่างชัดเจน.

## การทดสอบซ้ำส่วนปฏิบัติการและการแก้ badge แอดมิน

ระหว่างรัน UAT ที่คืนสภาพข้อมูลทดสอบต่อเนื่อง พบว่า assertion ของ badge รายงานใหม่อาจตรวจเร็วกว่า request นับรายงานหลังผู้ดูแลยืนยันสิทธิ์เสร็จ จึงทำให้ browser test รอบที่สองล้มเหลว แม้ API และรายการรายงานทำงานปกติ แก้โดยรอการโหลดจำนวนรายงานใหม่ในขั้นตอนยืนยันสิทธิ์ และปรับ test ให้รอ badge ปรากฏก่อนตรวจสถานะ

ผลทดสอบซ้ำ `verify-feedback-ui.mjs` ติดต่อกัน 2 รอบผ่านทั้งคู่ โดยรายงานทดสอบถูกเปลี่ยนเป็น `resolved` ทุกครั้ง นอกจากนี้ `pnpm test` ผ่าน **28 tests / 11 files**, `verify-table-ui.mjs` ยืนยันการคืนโต๊ะ 02 เป็นสถานะว่าง และ `verify-integration-readiness-ui.mjs` ยืนยันว่าแผง readiness ยังปกปิดข้อมูลลับและไม่ส่งธุรกรรมจริง.

## การส่งออกสรุปกะเป็น CSV

เพิ่มปุ่ม **ส่งออก CSV** ในส่วนสรุปกะ โดยใช้รายการธุรกรรมที่ผ่านตัวกรองวันที่ ช่องทางชำระเงิน และคำค้นหาปัจจุบันเท่านั้น ไฟล์เป็น UTF-8 พร้อม BOM เพื่อให้โปรแกรมสเปรดชีตอ่านภาษาไทยได้ถูกต้อง มีหัวตารางวันที่เวลา เลขอ้างอิง ลูกค้า ช่องทางชำระเงิน และยอดเงิน รวมถึงการ escape เครื่องหมายคำพูดในข้อมูลลูกค้า

ผลการยืนยัน: unit tests ผ่าน **29 tests / 11 files**, browser test `SHIFT_SUMMARY_UI_OK` ผ่านทั้งสรุปยอด breakdown ปุ่มพิมพ์ และการดาวน์โหลด CSV โดยไม่สร้างธุรกรรมใหม่, production build ผ่าน และเว็บไซต์สาธารณะตอบ `HTTP 200`.
