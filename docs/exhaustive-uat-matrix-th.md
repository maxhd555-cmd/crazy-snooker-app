# ตารางทดสอบครอบคลุมปุ่มและฟังก์ชัน — Crazy Snooker

> **ขอบเขต:** ทุกปุ่ม, ฟอร์ม, ตัวเลือก, กล่องโต้ตอบ และการนำทางที่แสดงจาก UI รุ่นปัจจุบัน การทดสอบไม่ส่ง LINE เพิ่ม, ไม่ยืนยันรับชำระเงินจริง และไม่ส่งอีเมลจริงโดยไม่มีการยืนยันข้อความปลายทางเฉพาะรอบ

| หมวด | จุดโต้ตอบที่ตรวจ | ลักษณะการยืนยัน | ข้อยกเว้น/การคืนสภาพ |
| --- | --- | --- | --- |
| นำทาง | เมนูทั้ง 8 หน้า, Help FAB, ปิด notice | เปลี่ยนหน้าและเปิด/ปิด dialog ได้ | ไม่กระทบข้อมูล |
| POS | สินค้าทุกรายการ, ค้นหาบาร์โค้ด, เพิ่ม/ลดจำนวน, กล้อง, สร้าง QR | ตะกร้า ยอดรวม และข้อความ error path ทำงาน | ไม่ยืนยันรับชำระเมื่อ PromptPay recipient ยังไม่ตั้งค่า |
| สมาชิก | เลือกสมาชิก, ยอดเติมเงิน, สร้าง QR | ควบคุมค่าบนหน้าและ error path ของการสร้าง QR | ไม่กดยืนยัน top-up |
| การจอง | ช่องข้อมูล, บันทึก, ปุ่มทดสอบใกล้หมดเวลา | Validation ครบถ้วน | ปุ่มที่ส่ง LINE จริงต้องใช้การยืนยันก่อนส่งเพิ่ม |
| คลัง | ค้นหาทุกกรณี, กล้อง, รับเข้า, ปรับออก, บันทึกจากบาร์โค้ด | เลือกสินค้าและปรับจำนวนในเบราว์เซอร์ได้ | state อยู่ใน local storage ของบริบททดสอบ |
| สถานะโต๊ะ | select ทุกสถานะ, เวลาเลิกเล่น, ป้ายเวลาเหลือ | API/SSE บันทึกเวลาและแสดงสถานะเวลา | โต๊ะ 02 กลับ `available` ใน finally block |
| ประวัติ/ใบเสร็จ | ตัวกรอง, รีเฟรช, เปิดใบเสร็จ, พิมพ์, เตรียมอีเมล | ใช้ API mock สำหรับ UI เพื่อไม่สร้างธุรกรรม | การพิมพ์และ mailto ไม่ส่งใบเสร็จจริง |
| Help/ทัวร์ | เปิด/ปิด, ค้นหา/ล้าง, รายงานปัญหา validation, ดาวน์โหลด PDF, ทัวร์ next/back/skip/restart | Dialog และ local storage ทำงานครบ | ดาวน์โหลดเป็นไฟล์ทดสอบ, ไม่ส่ง report จริงในกรณี validation |
| รายงานแอดมิน | ล็อกอิน, refresh, filters, badge, detail, status, note, ปิด dialog | ใช้ report `[TEST]` และตรวจสิทธิ์ API | ปิด report เป็น `resolved` ใน finally block |
| ชำระเงิน/บริการ | PromptPay QR, ยืนยันรับชำระ, ส่ง LINE, ส่งใบเสร็จเซิร์ฟเวอร์ | ทดสอบโค้ดและ error/readiness path | ฟังก์ชันที่สื่อสารหรือรับเงินจริงต้องมีข้อมูลตั้งค่าและ/หรือการยืนยันเพิ่มเติม |

## หลักเกณฑ์ผลการทดสอบ

ระบบถือว่าครอบคลุมเมื่อทุกปุ่มที่ไม่ก่อให้เกิดการสื่อสารหรือธุรกรรมจริงถูกเรียกจากเบราว์เซอร์อัตโนมัติอย่างน้อยหนึ่งเส้นทาง รวมทั้ง success/error state ที่เข้าถึงได้ ส่วนปุ่มที่ก่อให้เกิดการส่งข้อความหรือการเงินต้องระบุเหตุผลที่ไม่กด, วิธีทดสอบ readiness และข้อมูล/การยืนยันที่ยังต้องใช้ให้ชัดเจนในผลทดสอบ
